# Internationalisation

## Supported languages

`en` (default), `fr`, `de`, `pt`. Templates exist for these four only.

## Locale shapes we receive

Locales reach us in different shapes depending on where they come from:

| Source | Example values |
|---|---|
| Signup form language picker | `en`, `fr`, `de`, `pt` |
| Team invites (inviter picks from a regional list) | `fr-CH`, `de-CH`, `pt-BR`, `en-GB` |
| SSO identity providers (`locale` claim) | `pt_BR`, `de_DE`, `FR` |
| Missing / unknown | `undefined`, `''`, `ja-JP` |

## Rule

Anything that picks a language (templates, emails, formatting) must turn the
raw locale into a supported language with `resolveLanguage(locale)` from
`src/i18n.js`. It ignores case, accepts `-` or `_` as separator, keeps the
base language and falls back to `en` when the language is not supported.

Never index a per-language table (for example `TEMPLATES`) with a raw locale:
`TEMPLATES['de-CH']` is `undefined` and silently falls back to English.

## Customer-facing guarantee

A customer receives every email in the language resolved from their locale,
whichever signup path created their account.
